# Code conventions

How the code is laid out and tested. Vocabulary follows `GLOSSARY.md`; decisions follow `docs/adr/` and the spec (#14).

## Modules

| Module | What | Package |
|---|---|---|
| `:core` | The prayer core: pure Kotlin/JVM, **no Android dependencies**. Owns every rule. | `app.mawaqeet.core` |
| `:app` | Android app: thin adapters (Compose screens, widgets, alarms, storage) around the core. | `app.mawaqeet` (`.ui.<screen>`, `.ui.theme`, later `.widget`, `.alerts`, `.data`) |

- adhan-kotlin is an `implementation` dependency of `:core` and is used only in `core/.../Calculation.kt`. Its types never appear in the core's public interface; the core has its own `Prayer`, `CalculationMethod`, `AsrConvention`.
- Library versions live in `gradle/libs.versions.toml`. AGP 9 has built-in Kotlin: never apply `org.jetbrains.kotlin.android` in `:app`.

## The core's interface

- `PrayerCore(settings: PrayerSettings, clock: java.time.Clock, log: PrayerLogRepository)`. It is cheap to build; create a new one when settings change. The current instant always comes from the clock, never from `Instant.now()`.
- Queries are methods returning immutable data classes (`displayDay(): DisplayDay`). New queries from the spec (Prayer Day lookup, Prayer Log commands, weekly summary, week grid, alert plan, location change check, country defaults) are added as further methods or as collaborators passed to the constructor (e.g. a Prayer Log repository interface the app implements).
- Times are `java.time.ZonedDateTime` in the location's zone; calendar days are `LocalDate` at the location, never the device's zone.
- Display rules (Jumu'ah, Sunrise never being the next Prayer) are answered by the core (`PrayerTime.isJumuah`, `DisplayDay.next`), so the app and widgets never re-derive them.

## The Prayer Log

- A **Prayer Day is identified by a `LocalDate`**: the local calendar date of its Fajr at the place the user was that day. Its identity never depends on the Calculation Method or any other setting; only its times do. `PrayerCore.prayerDayAt(instant)` / `currentPrayerDay()` / `prayerDay(date)` return a `PrayerDay` with its times, each Prayer's `LogState` (`PRAYED`, `NOT_MARKED`, `NOT_YET_DUE`) as of the clock, and `isEditable`.
- Writes go only through `PrayerCore.mark` / `unmark(date, prayer)`, which return a `LogCommandResult` (`DONE`, `NOT_YET_DUE`, `OUTSIDE_EDIT_WINDOW`). The edit window is the current Prayer Day plus the 6 previous ones.
- `PrayerLogRepository` (in `:core`) is plain storage keyed by (Prayer Day date, `Prayer`) plus the first-use date; every rule stays in the core. Its methods are synchronous and may block, so the app calls the core's log queries and commands on `Dispatchers.IO`. Tests use `InMemoryPrayerLog` in `core/src/test`.
- Android: `app.mawaqeet.data.RoomPrayerLogRepository` over `PrayerLogDatabase` (Room, file `prayer_log.db`, schemas exported to `app/schemas/` and committed). Prayer Days are stored as ISO dates (`2026-11-08`), Prayers as enum names; only prayed entries have rows. A schema change needs a Room migration.
- There is one repository per process, `MawaqeetApplication.prayerLog`. Its `changes: StateFlow<Int>` moves after every write: screens re-query the core when it changes, and widgets must refresh on it too.

## Settings

- **Storage:** `app.mawaqeet.data.SettingsRepository` over one Preferences DataStore (file `datastore/settings.preferences_pb`, created once per process in `MawaqeetApplication`; DataStore allows only one instance per file). `settings: Flow<PrayerSettings>` emits the core's settings; add a key and a setter per new setting. Enums are stored by `name`, so enum entries may be reordered or added but never renamed; a missing or unknown name reads as `PrayerSettings.Default`'s value. App-only preferences (not core input) may live in the same store, exposed as their own flow.
- **Core input:** `MainActivity` collects `settings` and builds a new `PrayerCore` for each value (`remember(settings)`), so every screen follows a change immediately. Nothing is shown until the first value is read, so default times never flash.
- **Settings screen:** `ui/settings/SettingsScreen.kt` lists the six groups in the spec's order (Prayer Times, Alerts, Prayer Log, Language & display, Widgets, About), each a `SettingsGroup(titleRes) { ... }`. A ticket that adds settings replaces its group's `ComingSoon()` with its own private `XxxGroup` composable, adds callbacks to `SettingsActions` (implemented in `MainActivity` with the repository), and reuses `SettingRow` (opens a chooser) and `ChoiceRow` (radio option with a one-line description).
- **Alerts group (#23):** `ui/settings/AlertsGroup.kt`: one `SettingRow` per Prayer opening a dialog, then `SwitchRow`s (reusable on/off row) for alarm-clock mode, play on silent and vibration. Keys: `alert_<prayer>_adhan|sound|reminder|reminder_minutes` (prayer name lowercased), `alarm_clock_mode`, `play_on_silent`, `vibration`; a stored lead time below 10 reads as the default. Change several fields of one Prayer through `SettingsRepository.updatePrayerAlert(prayer) { it.copy(...) }` (read-modify-write inside one `edit`), never by copying the value the screen last saw: quick successive taps would overwrite each other.
- **Calculation Methods:** `CalculationMethod` order is the order Settings lists them; their Arabic and English names and one-line descriptions are `method_<name>` / `method_<name>_description` strings.
- **Spot-checks:** `core/src/test/.../CalculationSpotCheckTest.kt` compares the core with official published timetables within ±1 minute. Each table cites its source; add new ones only from a real published source.

## Location

- **Stored location:** `SettingsRepository.setLocation(SavedLocation)` / `savedLocation: Flow<SavedLocation?>` (null until the user sets one; `settings` then uses `PrayerSettings.Default.location`) / `clearLocation()`. `SavedLocation(location, source, city)`: `source` is `LocationSource.MANUAL` (city search or typed coordinates) or `AUTOMATIC` (#24); a manual location never changes by itself. `city: CityRef?` (id, English and Arabic name, country, `isNear`) names it without loading the city list: Home and Settings show it via `ui/location/locationName(saved)` ("near <city>" when `isNear`). Keys: `location_latitude`, `location_longitude`, `location_zone`, `location_source`, `location_city_id`, `location_city_name`, `location_city_name_ar`, `location_country`, `location_near_city`.
- **City list:** asset `app/src/main/assets/cities.tsv` (~34k GeoNames cities15000 places, ~1.0 MB compressed in the APK), regenerated only by `python3 -I tools/cities/generate_cities.py` (downloads at generation time; the build never needs the network). Read it through the core: `CityDirectory.read(stream)`, held once per process as `MawaqeetApplication.cities` (lazy; first touch off the main thread). `search(query, limit)` (Arabic or English, folds case, diacritics, hamza forms, ة/ه, ى/ي, optional «ال»; whole name, then prefix, then word start; larger cities first), `byId(id)`, `nearest(lat, lon): NearestCity` (`city`, `distanceKm`, `location` = the point with the city's zone; `toSavedLocation()`), `City.location` / `City.ref()` / `displayName(arabic)`.
- **Time zone of a point:** there is no zone-boundary data; typed coordinates (and any other point) take the IANA zone of the nearest bundled city. The Location screen says so. Near a zone or country border this can pick the neighbour's.
- **Country defaults:** `CountryDefaults.suggestionFor(countryCode): MethodSuggestion(countryCode, method, asrConvention)`; the country is the nearest bundled city's. The table is ADR 0003; change both together. Country names come from the platform (`Locale.getDisplayCountry`), not the dataset.
- **Prayer Days are fixed by place:** the location of past Prayer Days is kept as `PastPlace(until, location)` rows in `PrayerLogRepository` (`pastPlaces()` / `addPastPlace`; Room table `past_place`, DB version 2). A Prayer Day before an entry's `until` (and on or after the previous one's) is computed at that entry's location; the Prayer Day in progress at a change and every later one use the current settings' location. Only the location is frozen: a Calculation Method or Asr Convention change still recalculates every day. The Fajr boundary (`prayerDayAt`) uses each day's own place. A Prayer marked before travel stays `PRAYED` even if its new time is later.
- **Changing the location:** always through `MawaqeetApplication.locationUpdater` (`LocationUpdater.change(saved)`), never `SettingsRepository.setLocation` directly: it calls `PrayerCore(oldSettings, …).recordLocationChange()` first, then saves the location and clears the possibly-stale flag.
- **Automatic location and travel:** `app.mawaqeet.location.DeviceLocation` reads `ACCESS_COARSE_LOCATION` only, through `LocationManagerCompat` (fused if present, then network, then GPS; no Google Play services), only while the app is open. On every resume `MainActivity` passes the fix to `LocationUpdater.onDevicePosition(lat, lon)`, which applies the core rule `LocationChangeCheck.check(stored, lat, lon)` (moved more than 10 km: automatic → `Updated`, a short note on Home; manual → `Ask`, a dialog whose "Update" saves it as automatic; a declined move is not asked again in that process). The new place is `cities.nearest(...).toSavedLocation(LocationSource.AUTOMATIC)`. `ACTION_TIMEZONE_CHANGED` (in `RescheduleReceiver`) only sets `SettingsRepository.locationMaybeStale` (key `location_maybe_stale`); Home shows a hint until the next check or change.
- **Permission flow:** `ui/location/rememberLocationPermissionRequest(onResult)` returns a `LocationPermissionRequest`; `start()` shows the explanation (used only for Prayer Times, never leaves the phone), then the system request. Denial or "Not now" gives `false` and the caller falls back to city search. Onboarding reuses it.
- **Credits (About, #33):** GeoNames (CC BY 4.0, https://www.geonames.org/) and Natural Earth (public domain); text in `app/src/main/assets/licenses/cities.txt`.

## Dates, digits and language

- **One formatter:** every time, countdown, date and number the user sees goes through `app.mawaqeet.core.DisplayFormatter(locale, digitStyle)` (`time`, `countdown`, `gregorianDate`, `hijriDate`, `number`, `signedNumber`). Screens, notifications and widgets never build their own `DateTimeFormatter` or `String.format` for display; add a method to `DisplayFormatter` (with core tests in Arabic and English) when a new shape is needed. Machine strings use `Locale.ROOT`, never the formatter.
- **Hijri:** `HijriDate.of(date, offsetDays)` (Umm al-Qura via `java.time.chrono.HijrahDate`) gives plain numbers; `DisplayDay.hijriDate` already has the user's offset (`PrayerSettings.hijriOffsetDays`, `PrayerSettings.HIJRI_OFFSET_RANGE` = -2..2). Month names live only in `DisplayFormatter`; never use a platform Islamic-calendar formatter.
- **Digits:** `DigitStyle` (`AUTOMATIC` / `ARABIC_INDIC` / `WESTERN`) is an app-only preference (`SettingsRepository.digitStyle`), not core input. `DisplayFormatter` applies it as a `-u-nu-` extension and passes the resulting `DecimalStyle` to `java.time`.
- **In Compose:** `MainActivity` wraps its content in `ProvideDisplayFormatter(digits)` (`app/.../ui/DisplayFormatting.kt`); read `LocalDisplayFormatter.current`. Outside Compose screens (notifications, receivers, widgets) use `displayFormatter(context, digits)`.
- **Language:** `AppCompatDelegate.setApplicationLocales(LocaleListCompat.forLanguageTags("ar"|"en"))` from Settings, Language & display; the activity is recreated. The locale config is generated (`generateLocaleConfig`). Wrap a signed or Latin-script value inside Arabic text with `BidiFormatter.unicodeWrap` so `+1` never shows as `1+`.

## Alerts

- **Plan (core):** `PrayerCore.alertPlan(): AlertPlan` = `alerts: List<PlannedAlert>` (time order, due strictly after now and within `AlertPlan.WINDOW` = 48 h) + `nextLocalMidnight`. A `PlannedAlert` has `instant`, `prayer`, `kind` (`AlertKind.ADHAN_ALERT` / `PRAYER_REMINDER`), `sound` (`AlertSound.ShortAdhan` / `FullAdhan` / `FajrFullAdhan` / `CustomAdhan(reference, replaces)` / `Silent`), `deliveryMode` (`DeliveryMode.EXACT` / `ALARM_CLOCK`), `prayerDay` and `isJumuah`. Per-Prayer alert settings, reminders and alarm-clock mode are decided in the core from `PrayerSettings`; the adapter only follows the plan.
- **Scheduling (app, `app.mawaqeet.alerts`):** call `AlertRescheduler.reschedule(context)` (suspend, serialised) for any reason to re-plan; receivers use `rescheduleAsync(this, context)`. It is already called on boot, locked boot, time set, time-zone change, `MY_PACKAGE_REPLACED`, exact-alarm grant (`RescheduleReceiver`), every alarm (`AlertReceiver`), every settings value (`MawaqeetApplication.onCreate` collects `settings.settings`, so a new setting needs no extra wiring) and when the Grant screen is passed. `AlertScheduler.apply(plan)` reconciles and stores; never call `AlarmManager` for alerts elsewhere.
- **Locked boot:** before the first unlock DataStore (credential-encrypted) is unreadable, so `rearmStoredPlan(now)` re-arms the copy in device-protected storage: `createDeviceProtectedStorageContext().filesDir/alert_plan.txt` (`AlertPlanStore`, versioned text format; bump the version line on change). Backup rules (#25): `domain="device_file" path="alert_plan.txt"`, exclude it (it is regenerated).
- **Alarms:** request code = stable function of (Prayer Day, Prayer, kind) (`PlannedAlert.requestCode`, also the notification id); the display alarm uses request code 0 and action `AlertReceiver.ACTION_MIDNIGHT`, at `AlertPlan.nextDisplayChange` (local midnight, or an earlier Prayer Time whose Adhan Alert is off, so the display day still moves on there; the stored plan keeps only midnight). `AlertReceiver` (direct-boot aware) handles `ACTION_ALERT` (see Adhan playback below) and `ACTION_MIDNIGHT`; it is where the Adhan player (#22) starts, and both refresh the widgets (`rescheduleAsync(..., refreshWidgets = true)`).
- **Permission gate:** `AlertPermissions.of(context)` (notifications enabled; exact alarms via `canScheduleExactAlarms()` on 12+, always true before). `MainActivity` re-checks on every resume and shows `ui/permissions/GrantScreen` instead of everything else while either is missing. Robolectric denies exact alarms by default: activity tests need `AlertPermissionsRule` (rule `order = 0`, compose rule `order = 1`).
- **Alert settings (#23):** `PrayerSettings.alerts: AlertSettings` = per-Prayer `PrayerAlertSettings(adhanAlert = true, sound: AdhanSoundChoice = SHORT|FULL|SILENT, reminder = false, reminderMinutes = 15)` (`alerts.of(prayer)`, `alerts.with(prayer, …)`; init rejects `reminderMinutes < PrayerAlertSettings.MIN_REMINDER_MINUTES` = 10) plus `alarmClockMode`, `playOnSilent`, `vibration`, and the master switch `enabled` (DataStore `alerts_enabled`, Settings → Alerts → All app alerts): off, `alertPlan()` holds no alerts at all (so applying it cancels every alarm) and the display alarm moves at each Prayer Time; Home and the Next Prayer widget read `alerts.effective(prayer)`, which shows every Prayer as off. The core maps them in `alertPlan()`: `FULL` on Fajr → `AlertSound.FajrFullAdhan`; a Prayer Reminder is an extra `PlannedAlert(kind = PRAYER_REMINDER, sound = AlertSound.ReminderTone, deliveryMode = EXACT)` at `prayerTime - reminderMinutes` (never an alarm clock, so the lock screen shows the Prayer); alarm-clock mode makes Adhan Alerts `ALARM_CLOCK`. Settings the receiver needs before the first unlock travel with every alert: `PlannedAlert.prayerTime`, `playOnSilent`, `vibration` → stored plan (`alert-plan-v3`) and the alarm intent (`EXTRA_KIND`, `EXTRA_PRAYER_TIME`, `EXTRA_PLAY_ON_SILENT`, `EXTRA_VIBRATION`). Never read DataStore in `AlertReceiver`; a new fire-time setting goes the same way (field on `PlannedAlert`, store version bump, intent extra).
- **Prayer Reminders on Android:** never reach the player. `AlertOutput` posts them on channel `prayer_reminders` (IMPORTANCE_DEFAULT, system default notification sound, no channel vibration; the app vibrates per `decide`) when `decide` returns `play = ReminderTone`, else on the silent `adhan_alerts` channel. The notification counts down to the Prayer Time (`setUsesChronometer` + `setChronometerCountDown`), so it needs no digit formatting before unlock.
- **Notification icon:** every notification (Adhan Alerts and Prayer Reminders, `AdhanNotification.builder`) uses `R.drawable.ic_notification`, the launcher's monochrome mihrab cropped for the status bar, never a system alarm icon.
- **Adhan playback (#22):** `AlertReceiver` asks the core `AlertPlayback.decide(sound, DeviceAudio(ringer, inCall), late, playOnSilent, vibration)` → `AlertPlayback(play: AlertSound?, vibrate)`; `AlertOutput.deliver` carries it out (vibrates itself, then starts `AdhanPlayerService` or posts the plain notification). Rules live in the core only: silent → nothing, vibrate → vibration only (with `playOnSilent` the adhan also plays in silent/vibrate, never a `ReminderTone`; silent never vibrates; `vibration = false` never vibrates), during a call (`AudioManager.mode` in call/communication/ringtone) anything but the Short Adhan is skipped, an alert delivered more than `AlertPlayback.MAX_LATENESS` (10 min) late is never played aloud. The alarm stream ignores the ringer, so this check is the only thing respecting silent mode. Alarm intents carry `EXTRA_SOUND` (`encodeAlertSound`, shared with `AlertPlanStore`) and `EXTRA_AT` (planned epoch millis).
- **Player:** `AdhanPlayerService` (`mediaPlayback` FGS, direct-boot aware, `START_NOT_STICKY`) plays `AdhanSounds.uri(...)` with `USAGE_ALARM`, fades in over 3 s, holds `AUDIOFOCUS_GAIN_TRANSIENT`, and is the foreground notification (`AdhanNotification(prayer, isJumuah, id = requestCode)`) with Stop (also its delete intent). On finish/Stop it re-posts the notification without Stop. Notification content and actions shared by all paths come from `AdhanNotification.builder(context, channel)`.
- **Audio assets:** `res/raw/adhan_placeholder` (Short Adhan), `adhan_full` (Full Adhan) and `adhan_fajr_full` (Fajr's Full Adhan) are generated by `generate<Variant>AdhanPlaceholder` (`app/build.gradle.kts`): `-Pmawaqeet.adhanAudio=<file>`, `-Pmawaqeet.adhanFullAudio=<file>` and `-Pmawaqeet.adhanFajrAudio=<file>` bundle those recordings in every build, release included (kept outside the repo because the repo is public and the recordings aren't ours to publish). Without `adhanAudio`, debug builds copy `dev-assets/short-adhan-dev.*` (override the folder with `-Pmawaqeet.devAssets=<dir>`), and anything else gets a 1 s silent WAV; a missing Full or Fajr recording reuses the Short Adhan's clip. Never add adhan audio to git or `src/`. `AdhanSounds.bundled` maps each `AlertSound` to its raw name.
- **Release signing:** `./gradlew :app:assembleRelease` signs with the keystore named by the Gradle properties `mawaqeet.signing.storeFile`, `storePassword`, `keyAlias`, `keyPassword` (put them in `~/.gradle/gradle.properties` or pass `-P`; or the env vars `MAWAQEET_SIGNING_STORE_FILE` etc.). Without them the release APK is unsigned. The keystore and its passwords never go in the repo (`*.jks`/`*.keystore` are git-ignored); losing the keystore means no update can install over an existing copy.
- **Custom Adhan (#28):** `AlertSettings.customAdhans: Map<AdhanRecording, String>` (`SHORT`, `FULL`, `FAJR_FULL`; `customAdhan(recording)`, `withCustomAdhan(recording, reference | null)`). Each recording is replaced on its own: a Custom Adhan for `FULL` never changes Fajr, which keeps `FAJR_FULL` (its own adhan with «الصلاة خير من النوم») until a Custom Adhan is chosen for `FAJR_FULL` itself. `AdhanRecording.of(prayer, choice)` picks the recording; the plan's sound is `AlertSound.of(recording, alerts)` = `CustomAdhan(reference, replaces = recording)` or the bundled sound. The reference is a content URI the core never opens. A Custom Adhan follows the bundled audio's fade-in, silent-mode and lateness rules, and during a call is skipped like the Full Adhan (its length is unknown, even as the Short Adhan). Stored as `CUSTOM:<RECORDING>:<uri>` in the plan and intents; DataStore keys `custom_adhan_short|full|fajr_full`.
- **Custom Adhan on Android:** Settings → Alerts picks the file with `ActivityResultContracts.OpenDocument` (`audio/*`); `SettingsActions.setCustomAdhan` takes a persistable read permission (`CustomAdhanFiles.keep`) before storing, and `SettingsRepository.setCustomAdhan` returns the references no recording uses any more, whose permissions are released. `AdhanPreview` plays a choice once on the alarm stream. `CustomAdhanFiles.readableName` checks each chosen file on every resume of Settings; an unreadable one shows a notice there. `AdhanPlayerService` falls back to `AdhanSounds.bundled(sound)` (the replaced recording) when the file can't be opened or decoded, including before the first unlock when the provider may be unavailable.
- **Prayer Silence (#57):** `AlertSettings.prayerSilence: PrayerSilence(enabled, mode = SILENT|VIBRATE, prayers, minutes, jumuahMinutes)`; `stepped(jumuah, steps)` moves a duration by `MINUTES_STEP` within its range. `alertPlan()` holds `silenceWindows: List<SilenceWindow>` (master switch or not). `AlertScheduler` sets an end alarm per window and a start alarm only when no Adhan Alert opens it (`AlertReceiver` starts it once the adhan stops, via `PrayerSilencer.awaitAdhan`/`adhanStopped`); both go to `SilenceReceiver`. `PrayerSilencer` is the only code that touches the ringer: it silences only a phone on normal sound with Do Not Disturb off, records (device-protected prefs `prayer_silence`) the mode it replaced and the ringer and interruption filter it left, and at the end restores only if both are still as it left them (the user's change wins). An overlapping window extends the held one to the later end. Every applied plan goes through `PrayerSilencer.replan`: a held window that left the plan, or now ends before now, ends at once; one with a new end follows it. `isActive(now)` tells Worship Reminders to post silently. Needs Do Not Disturb access: Settings explains, opens the system page and stores the switch on only once access is given.
- **Receivers' notification style:** the rescheduler stores the app's digits and language with the plan (`NotificationStyle`, the stored plan's `style` line, `alert-plan-v7`; v6 is still read); `PrayerSilencer` reads them from there. Receivers never read DataStore for them.
- **Worship Reminders (#59):** `AlertSettings.worshipReminders: WorshipReminders(salawat, kahf, morningAdhkar, eveningAdhkar)`, planned by `PrayerCore.alertPlan()` as `worshipReminders: List<PlannedWorshipReminder(kind, instant, prayerDay, slot)>` (none with the master switch off). A new kind adds a field, an entry at the END of `WorshipReminderKind`, a branch in `PrayerCore.worshipReminders()` and its copy in `WorshipReminderNotification`. Exact alarms (request codes `4_000_000 + day×128 + kind×32 + slot`) go to `WorshipReminderReceiver`, which drops an adhkar reminder whose set is already complete and posts silently during a Silence Window; channel `worship_reminders`, one notification per kind.
- **Receivers:** work that touches preferences, `AudioManager`, files or the database runs through `ReceiverWork.run(receiver) { ... }` (`goAsync`, then `Dispatchers.IO`; `rescheduleAsync` uses it too); tests wait with `ReceiverWork.idle()`. A receiver never launches a coroutine without `goAsync`.
- **Play fallback:** `-Pmawaqeet.adhanChannelSoundFallback=true` sets `BuildConfig.ADHAN_CHANNEL_SOUND_FALLBACK`: audible alerts post on channel `adhan_alerts_sound_v1` (bundled adhan as channel sound, `USAGE_ALARM`; dismissing stops it) and the `src/channelSoundFallback` manifest overlay removes the service and its FGS permissions. Channel sounds are immutable: a new sound needs a new channel id.

## Widgets

- **Layout:** package `app.mawaqeet.widget`. Per Widget Variant: `<Variant>Content.kt` (a pure data class + `of(day, now, formatter)` over the core's `DisplayDay` and `DisplayFormatter`, plain JVM tests in `app/src/test/.../widget/`) and `<Variant>Widget.kt` (the thin Glance `GlanceAppWidget` + its `GlanceAppWidgetReceiver`s). Resources: `res/xml/<variant>_widget_info.xml` (`initialLayout="@layout/glance_default_loading_layout"`, `updatePeriodMillis="0"`), `res/layout/widget_*.xml` for RemoteViews interop, strings `widget_*`, colours `widget_*` in `values/` and `values-night/` (light/dark), `widget_over_*` (light text over a see-through background) and `widget_dyn_*` (wallpaper colours: `@android:color/system_*` in `values-v31/`, `values-night-v31/`). Drawables are white and tinted at runtime. Glance 1.2.0 (`glance-appwidget` only); the system font. Prayer names: `prayerNameRes(prayerTime)` (Jumu'ah on Friday).
- **Refreshing:** one entry point, `Widgets.refreshAll(context)` (suspend; does nothing before the first unlock), or `Widgets.refreshAllAsync(receiver, context)`. It bumps `Widgets.REFRESHED_AT` in each widget's Glance state and calls `update`; `Widgets.refresh(context, kinds)` does the same for some variants only. A widget computes its content in `remember(settings, digits, language, currentState(Widgets.REFRESHED_AT)) { ... }` inside `provideContent`, because a running Glance session recomposes instead of calling `provideGlance` again. It is called by the display alarms (`AlertReceiver`: each Prayer Time and local midnight), `RescheduleReceiver` (boot, time set, zone, app update, `LOCALE_CHANGED`) and `MawaqeetApplication` on every later change of `settings`, `digitStyle`, `appLanguage` or `widgetAppearance`. A new variant only adds its class to `Widgets.all`. Widgets never poll, with two approved exceptions: Next Prayer and its ring, whose progress moves every 30 minutes (`updatePeriodMillis=1800000`, the receivers' `onUpdate` refreshes them), and the three Clock widgets (below), re-rendered each minute. `MawaqeetApplication` also refreshes them on every `prayerLog.changes` (mark, unmark, delete), for the Prayer Log widgets (#31). Today with Prayer Log changes the log only through `ToggleMarkAction` (a tap on a due Prayer's column), which calls `PrayerCore.mark`/`unmark`, so the core's rules still decide.
- **Language and digits in a fresh process:** read `SettingsRepository.settings`, `digitStyle` and `appLanguage` (`first()` in `provideGlance`, then `collectAsState`). `appLanguage` is a copy of the per-app language that `MainActivity.onCreate` keeps in sync, because on Android 8–12 AppCompat only knows the per-app language in a process where an activity has run. Use `appLocale(context, appLanguage)` for the `DisplayFormatter` and `localizedContext(context, locale)` for strings; set the root's direction from the locale (`widget_root_rtl|ltr` container around the Glance content), since the launcher lays widgets out in its own language.
- **Shared parts (`WidgetParts.kt`):** a widget's `provideGlance` is `provideFromCore(context, build, layout)` (settings, digits, language and refreshes handled once; `build` gets a fresh `PrayerCore`), its frame is `WidgetFrame(rtl, ..., opens)` (direction root, background, and the widget's only tap target: `MainActivity.openIntent(context, Opens.TODAY | Opens.PRAYER_LOG)`, which `MainActivity` handles on launch and in `onNewIntent`, whatever screen was open) and the Gregorian-then-Hijri line is `DateLine(date)` (the Hijri date ellipsizes first). Every piece of text is `WidgetLine(text, sp, tone)`, a platform `TextView` (`widget_text_*` layouts) so it can ellipsize and carry a shadow; its colour comes from a `Tone` of the current `WidgetStyle`.
- **Appearance (#32):** Settings → Widgets stores `SettingsRepository.widgetAppearance` (transparency 0–100 in steps of 10, wallpaper or app colours). `WidgetStyle.of(appearance)` turns it into colour resources, the background's alpha and `shadowedText` (light text with a soft shadow from 60%). `provideFromCore` provides it as `LocalWidgetStyle`; `WidgetFrame` tints and fades the `widget_bg` image; images take `tint(style.x)`. App colours are the default; wallpaper colours exist only on Android 12+, and below it the app's colours always apply. Next Prayer (`provideFromCore(deep = true)`) always uses its deep teal and gold surface (`widget_deep_*`), whatever the choice.
- **Sizes:** on Android 12+ text grows in steps (`textStep(minWidth, minHeight)`: 1, 1.15, 1.3) with the room the launcher gives; on Android 8–11 a widget keeps one layout at its default size. Next Prayer uses `SizeMode.Exact` instead: 4×2 from 220dp wide, 2×2 below, and the 1×1 ring is its own receiver; its layouts grow up to `NextPrayerMetrics.MAX_GROW` (1.7×) to fill tall phone cells. Drawn parts (progress line, ring, star, Today's day path) are bitmaps from `WidgetArt`.
- **Glance pitfalls:** a `Row` or `Column` keeps at most 10 children (extra ones are dropped silently), so make gaps with padding, not `Spacer`s (before Android 12 Glance also sizes a `Spacer` with a hidden 14sp text, which makes a small line taller); an `AndroidRemoteViews` fills its parent unless given `wrapContentWidth()`/`wrapContentHeight()` (`WidgetLine` does this); `setGravity` isn't remotable before Android 12, so centre text with a Glance `Box`.
- **No clipped text:** sizes that must fit live in a `<Variant>Metrics` object. `WidgetTextFitTest` measures the widest names and times with the real system font (`@GraphicsMode(NATIVE)`), and the `*RenderTest`s render each widget (also at 70% transparency and on Android 11, `WidgetAppearanceRenderTest`) with `GlanceAppWidget.compose` at its smallest size and checks every `TextView` fits. Arabic lines are taller than Latin ones (fallback line spacing), which matters at 4×1 and 2×1: measure with `lineHeightDp`.
- **Clock widgets (#56):** Big Clock, Gold Clock and Clock & Prayer are listed in `Widgets.clocks` (their receivers in `Widgets.clockReceivers`); a new Clock variant adds itself to both. Their content is `ClockContent.of(day, now, formatter, twentyFourHour)` (the previous and next Stop, where a Stop is a Prayer or Sunrise, the bar, the countdown, the clock and the dates; before Fajr the previous Stop is `DisplayDay.previousIsha`, the previous day's own Isha), built through `clockContent(context, day, text, clock)`, which also arms the next re-render. The widget classes take a `java.time.Clock` (the system clock by default) for `provideFromCore` and `clockContent`; render tests pass a fixed one. The minute tick is `ClockTickReceiver` (a non-wakeup `RTC` alarm at `ClockContent.nextChange`, re-armed by each render), cancelled synchronously from the receivers' `onDisabled` when the last Clock widget is removed; the launcher ticks the clock face itself (`TextClock`).
- **Countdown:** a count-down `Chronometer` through `AndroidRemoteViews` (`setChronometer(id, elapsedRealtime() + untilNext, "بعد %s", true)` + `setChronometerCountDown`). The launcher formats its digits in the device language, so they may not follow the digit setting.

## Adhkar

- **Catalog (#58):** asset `app/src/main/assets/adhkar.tsv` (header `# mawaqeet-adhkar-v1`; tab-separated `set id count source text`, `\n` for line breaks; unknown sets are skipped), read once per process as `MawaqeetApplication.adhkarCatalog` (`AdhkarCatalog.read`, first touch off the main thread). Dhikr ids are stable: stored progress refers to them.
- **Rules (core):** `Adhkar(catalog, PrayerCore, AdhkarRepository)`: progress, count, restart and `isComplete` per `AdhkarSlot` (`MORNING`, `EVENING`, or after a Prayer, key `after-prayer:<prayer>`) and Prayer Day; a set is recorded only if finished in its time. The Adhkar Record (week grid) and Tasbeeh (total under the reserved `tasbeeh` key) are core queries too. Tests use `InMemoryAdhkarRepository`.
- **Android:** `RoomAdhkarRepository` on the Prayer Log's database (`adhkar_progress`, `adhkar_record`, `adhkar_first_use`); deleting the Adhkar Record (Settings → About & your data) also clears Tasbeeh. The screen is `ui/adhkar/AdhkarScreen.kt`, a tab between the Prayer Log and Settings; it loads off the main thread, so screen tests wait for its text before clicking.

## Qibla

- **Rules (core):** `Qibla.from(latitude, longitude)` gives `bearing` (initial great-circle bearing to the Kaaba, degrees from true north, 0 until 360) and `distanceKm`; `turn(heading)` gives the hint `QiblaTurn(degrees, side = RIGHT|LEFT|ON_TARGET)` the short way round (`ON_TARGET_DEGREES` = 3); `direction` is the nearest of the eight `CompassPoint`s. Tests: `QiblaTest`.
- **Tools Row (#88):** `ui/home/ToolsRow.kt`, passed to `HomeScreen(tools = …)`; equal 48dp buttons in `EqualRowOrStack` (stacked full width when a label won't fit, e.g. at 200% text), a tool with a null callback is hidden. `HomeFitTest` renders the real row.
- **Screen:** `ui/qibla/QiblaScreen(location, headings, onSetLocation, onBack, onFacingQibla)`, opened from `MainActivity` (`showQibla`) with `savedLocation?.location` only (null → «تحديد الموقع», which opens the Location screen). Headings come from `app.mawaqeet.qibla.HeadingSource`: `SensorHeadings` (rotation vector, else accelerometer + magnetometer, plus `GeomagneticField` declination; `accurate = false` on low or unreliable magnetometer accuracy shows the figure-8 card), collected with `collectAsStateWithLifecycle`, so the sensors are registered only while the screen is visible. `hasSensor = false` shows the bearing-only card. The dial's N/E/S/W and Kaaba marker are placed with absolute `place`, never `placeRelative`, so RTL never mirrors east and west. Tests use a fake `HeadingSource` (`QiblaScreenTest`).
## Hijri Calendar

- **Core (#93):** `HijriCalendar(offsetDays)` (pure): `day(date)` / `days(first, last)` give `CalendarDay(date, hijri, occasions: Set<Occasion>, fasts: Set<SunnahFast>, fastingForbidden)`. `Occasion` is the fixed table (Hijri month and day range; a run reaching 30 ends on the month's last day); `SunnahFast` kinds are `MONDAY_THURSDAY`, `WHITE_DAYS`, `ARAFAH`, `ASHURA` (9–10 Muharram), `SIX_OF_SHAWWAL` (2–7 Shawwal). Forbidden Fast Days (the Eids, Tashreeq) carry no fasts; Mondays/Thursdays and white days are not Sunnah Fasts in Ramadan. `upcoming(today)` is the «القادم» list: `Upcoming.OccasionDays` / `Upcoming.FastDays` with `first`, `last`, `daysAway` (0 for today or under way). Tests: `HijriCalendarTest`, `UpcomingTest` (dates from the published Umm al-Qura calendar).
- **Screen:** `ui/calendar/CalendarScreen(calendar, today, onBack)`, opened from `MainActivity` (`showCalendar`) by the Tools Row's «التقويم» and the date line on Today (`HomeScreen(onOpenCalendar = …)`), with `today = core.displayDay().date`. Tabs are `CalendarTab` (the month grid, #94, adds its entry; with one tab the switcher shows as a heading). Occasion and fast names: `Occasion.label`, `SunnahFast.label`. Tests: `CalendarScreenTest`, `CalendarOpensTest`.

## Backup File

- **Core (#98):** `Backup.export(snapshot, exportedAt): ByteArray` writes a `BackupSnapshot(settings, prayerLog: PrayerLogBackup, adhkarRecord: AdhkarRecordBackup)` as the versioned JSON documented on `Backup` (`format` = `mawaqeet-backup`, `version` = `Backup.VERSION`, `exportedAt`, then `settings`, `prayerLog`, `adhkarRecord`; keys, days and set members sorted). `settings` is every stored setting by its DataStore key (`SettingValue.Flag|Whole|Decimal|Text|TextSet`), so a new setting is in the file with no backup code; `Backup.fileName(date)` names the file. A format change readers can't ignore bumps `VERSION`.
- **Restore core (#99):** `Backup.restore(bytes, current): RestoreResult` reads a file and merges it with the phone's own snapshot: `Restored(snapshot)` is what the phone should hold (settings replaced wholesale except `Backup.restorable` keys; Prayer Log and Adhkar Record a union; each first-use date the earlier; the file's past places only before the phone's earliest `until`, all of them on a phone that never moved), `NewerVersion` for a `version` above `VERSION`, `Damaged` for anything else unreadable. Unknown fields are ignored.
- **Android:** `MawaqeetApplication.backup` (`data/BackupFiles.kt`) gathers the snapshot (`SettingsRepository.backupSettings()`, `RoomPrayerLogRepository.backup()`, `RoomAdhkarRepository.backup()`) and writes it to the document the user created with `ActivityResultContracts.CreateDocument("application/json")` (Settings → Backup, `ui/settings/BackupPage.kt`); no permission, no network. Keys about this phone stay out of the file and are never taken from one (`Backup.PHONE_ONLY_KEYS`: `backup_last_export`, `location_maybe_stale`, `onboarding_done`, `fix_alerts_done`, plus every `Backup.CUSTOM_ADHAN_PREFIX` key); a new phone-only key goes there. A new Long setting goes in `SettingsRepository.LONG_KEYS` (every other whole number restores as an Int). The last export time is `SettingsRepository.lastBackupExport` (key `backup_last_export`, epoch millis), written only after the file is.
- **Android restore (#99):** `BackupFiles.restore(open)` picks with `OpenDocument`, after a confirmation dialog on `BackupPage`. It checks everything before writing (`SettingsRepository.canRestore` re-reads the new settings as the app does, so a value of the wrong kind refuses the whole file), then writes the records in one Room transaction, then `restoreSettings` (one DataStore edit), then its `afterRestore` hook (release dropped Custom Adhan permissions, `AlertRescheduler.reschedule`, `Widgets.refreshAll`). `RestoreOutcome.Restored(usesAlertPermissions)` makes the page offer Fix Alerts; `MainActivity` applies a restored app language.

## Accessibility

- **Checked by tests (#33):** `AccessibilityTest` renders Home, the Prayer Log and Settings at 200% font in a tall window, in Arabic and English, and fails on any cut-off or ellipsized text and any tap target under 48×48dp (`assertAccessible` in `Accessibility.kt`; call it from new screens' tests). `TalkBackTest` checks each Prayer is one item with its name, time and Prayer Log state. `ContrastTest` keeps text colour roles at 4.5:1 in both themes, app and widgets.
- **Rules:** decorative glyphs (the ✓ in a mark) get `clearAndSetSemantics {}`, since the row's state already says it. A row that toggles uses `Role.Checkbox` with a `stateDescription`. Colours on the Next Prayer card use `tertiary`, not the brand amber, which reads at 2.7:1 there.
- **Icon:** `mipmap-anydpi-v26/ic_launcher*.xml`, an adaptive icon with background, foreground and monochrome (themed) layers. `LauncherIconTest` keeps every mark inside the 66dp safe zone.
- **About:** `about/Credits.kt` lists every library, dataset, font and recording with its licence. `CreditsTest` fails when a shipped dependency or bundled font isn't credited, so add the credit with the dependency.

## Tests

- Nearly all tests are plain JVM tests in `core/src/test`, through the core's public interface only, with a fixed `Clock` (`Clock.fixed(...)`). No tests of internal classes or adhan-kotlin.
- Test names are backtick sentences stating the decision: `` `after local midnight the display day is the new date and the next Prayer is its Fajr` ``.
- Expected values come from an independent source (a published timetable, a worked example), never recomputed the way the code does.
- `:app` has only thin Robolectric tests (`@Config(sdk = [36])`). Robolectric defaults to `en-rUS`, so pin `@Config(qualifiers = "ar")` or `"fr"` (to prove Arabic is the fallback).

## Resources and look

- Arabic strings in `res/values/` (the unqualified default, `res/resources.properties`), English in `res/values-en/`. Write Arabic first.
- Colours: `ui/theme/Theme.kt` holds the brand palette as light and dark `ColorScheme`s; use `MaterialTheme.colorScheme`, not hex values, in screens.
- Fonts: `MaterialTheme.typography` display/headline/title styles are Noto Kufi Arabic (headings, large times); body/label styles are Noto Sans Arabic (running text and controls). Widgets use the system font.
- Font licences (OFL) are in `app/src/main/assets/licenses/` for the About screen.
